# 图片缓存清理（Issue #84）

## 用户行为

设置中的“清理”保留转圈加载，不显示百分比。文件与索引删除完成后结束转圈，随后更新实际剩余大小；失败时提示重试，不把失败显示为已清空。重复点击、重新进入设置页会连接同一个清理任务。

任务属于应用内缓存管理器，不属于设置页。离开设置页或应用进入后台不会取消清理；Android 用独立的 `image-cache` work owner 保留现有 Flutter engine，与离线下载和 APK 下载互不释放。没有新增前台服务、通知或系统调度任务。iOS 遵循系统挂起/恢复；进程被杀或重启后不自动续跑。完成提示只在设置页当前可见、应用处于前台时出现。

只清理普通图片缓存、Flutter 解码内存和阅读器回访内存；永久离线漫画、账号和设置不属于清理目标。缓存键、容量限制、持久化格式均不变。

## 清理链路

- 旧实现对全部索引逐个 `removeFile(key)`：每项再次查库、更新时间并删除；更新时间触发配额维护通知，设置页每次通知都可能扫描整个目录。
- 新实现保留一个清理 Future 和可观察状态，增加清理代次；暂停配额维护与通知，等待已经开始的大小统计和索引登记。
- 读取一次待删索引快照，最多 4 个 worker 使用 `store.removeCachedFile(entry)`。等待文件真正删除后才删索引；单项失败不阻止其他项，失败记录保留供重试。没有调用库中不等待文件删除的 `emptyCache`，也不递归删除缓存根目录。
- 清理期间新写入、会更新时间戳的缓存查询等待任务完成。旧流式写入只删除自己拥有的唯一文件；库内部下载和查询的异步索引登记通过 Zone 保留请求代次，旧代次不能覆盖新记录。旧排队请求返回 304 时保留当前索引仍在使用的文件。
- 结束时清除库内存索引，恢复配额维护并释放 Android owner。清理期间不启动新的大小扫描；管理器共享同一个扫描 Future，设置组件合并刷新请求，只补读最终结果。

## 可复现性能对照

使用项目约定的 Flutter 3.16，先执行 `flutter pub get`，再运行：

```powershell
python scripts/benchmark_image_cache_clear.py --flutter C:/flutter_v3.16.0/bin/flutter.bat
```

脚本从固定基线 `1fd4768275828a3ca7133a34b74ab37ee39a07b2` 提取原缓存管理器与配额实现到 `build/cache_clear_benchmark/`，不切换工作区。结果保存到该目录的 `results.json`。

对照使用 Windows 真实临时文件、flutter_cache_manager 3.3.1 的 JSON 索引；两组体积同为 5,120,000 字节：5,000 × 1,024 字节和 10 × 512,000 字节。每组分别测索引已初始化、索引尚未初始化，各 5 次，交替新旧执行顺序。计时包括清理完成和后续大小统计，另外记录索引查询、更新时间、删除及通知次数。计时阶段没有设置页扫描监听器，避免让基线的扫描风暴夸大优化收益。

这里的“冷”指索引未初始化，不代表清空操作系统磁盘缓存。JSON 索引与移动端 SQLite/平台通道不同，主机结果不能当作真机绝对耗时承诺。

2026-11-11 本机实测中位数（包含最终大小统计）：

| 文件布局 | 索引状态 | 原实现 | 新实现 | 耗时减少 |
| --- | --- | ---: | ---: | ---: |
| 5,000 个小文件 | 已初始化 | 6,253.35 ms | 1,251.29 ms | 80.0% |
| 5,000 个小文件 | 未初始化 | 6,217.62 ms | 1,281.94 ms | 79.4% |
| 10 个大文件 | 已初始化 | 14.87 ms | 5.71 ms | 61.6% |
| 10 个大文件 | 未初始化 | 29.42 ms | 14.31 ms | 51.4% |

5,000 文件组中，清理期间逐键查询从 15,001 次降为 0，更新时间从 5,000 次降为 0，合并监听的变化通知从 5,002 次降为 2。两版均执行一次待删快照和一次恢复配额的扫描、5,000 次索引删除；新实现没有用提前返回或漏删换速度。全部 40 次测量最终目录大小均为 0；满足计划中大量小文件中位数至少减少 50% 的主机对照目标。[本次原始测量记录](validation/issue84-cache-clear.json)。
