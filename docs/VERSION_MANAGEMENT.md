# OViewer 版本管理实施方案

## 1. 目标与基本规则

- **应用版本号自动计算**：根据上个正式版本之后各项改动的实际性质和兼容性确定；提交前缀不能单独决定升级幅度。
- **内部构建号自动分配**：由统一入口分配，两平台共用。
- **同一候选跨分支复用版本**：从 `dev` 合并到 `main`，不因分支变化再次升号。
- **正式发布仍由用户手动发起**：自动化负责校验和发布已验证的安装包，不自行决定发布时机。
- **每次推送后检查并拉取自动版本提交**：核对本次推送对应的候选准备任务，等待其结束或确认未触发，再快进拉取远程最新版本号、候选记录及其他提交；本地所推送分支必须与其对应远端一致，不能把拉取推迟到下一次修改。失败时也要检查已写回的提交并报告实际状态，不手动补号或强制覆盖。
- **正式发布前与收尾后，本地及远端 `main`、`dev` 四个分支必须指向同一提交**：完整同步代码、文档、发布记录和自动版本提交；归档日志后再次同步，确认 `dev`、`main`、`origin/dev`、`origin/main` 四行 SHA 相同。只同步远程或只保证应用代码相同均不满足要求。之后正常开发可继续推进 `dev`；正式标签仍固定在已验证候选提交。
- **正式发布禁止擅自新建独立工作树**：本地发布操作默认在当前工作区进行；未经用户明确授权，不得通过 `git worktree add`、工具或脚本创建独立工作树。一般的“正式发布”指令不包含创建工作树的授权，具体约束见[发布操作文档](RELEASING.md#正式发布的工作区约束)。
- 已发布的 `v1.0.0`、标签和附件保持不变。

分支职责：

| 对象 | 用途 |
|---|---|
| `dev` | 日常开发，推送有效改动后准备测试候选 |
| `main` | 已确认的稳定代码，准备正式发布 |
| `version-state` | 自动化维护的版本分配台账，不用于开发或构建 |
| `vX.Y.Z` 标签 | 固定指向正式安装包对应的候选提交 |
| GitHub Release | 分发经过验证的原始 APK、IPA |

不再手动填写每个候选的版本号。脚本计算完成后，统一回写 `pubspec.yaml`；它仍是两平台构建读取版本的唯一配置文件。

## 2. 自动版本计算与候选识别

### 应用版本号

以最近正式 Release 的版本为基准，分析该版本标签之后的有效提交，采用最高级别的实际变更。不要以上个测试候选的 X.Y.Z 为基准，避免误标候选永久抬高正式版本。

| 改动性质（`Change-Kind`） | 判断依据与规则 | 以 `1.0.0` 为基准 |
|---|---|---|
| `breaking` | 破坏既有兼容性，例如旧数据格式或已有接口不再可用；升 X，Y/Z 归零 | `2.0.0` |
| `feature` | 新增此前不存在的独立业务能力，例如首次提供离线阅读；升 Y，Z 归零 | `1.1.0` |
| `fix`、`enhancement` | 修复既有功能，或调整原有流程、确认交互、状态提示、文案和布局；升 Z | `1.0.1` |
| `performance` | 性能或动画速度优化，兼容性与业务能力不变；升 Z | `1.0.1` |
| `maintenance` | 重构、测试、构建、CI、依赖及发布工具维护等有效变更；按项目约定升 Z | `1.0.1` |
| 仅 Markdown、文档或许可证变更 | 不生成新候选，不升号 | 保持原版本 |

提交标题继续遵循 [Conventional Commits](https://www.conventionalcommits.org/en/v1.0.0/)，但版本计算采用经审阅的实际改动分类。比如在既有“检查更新”中增加确认弹窗、调整提醒显示与持久化属于 `fix` / `enhancement`，不会仅因代码增加或标题写了 `feat` 就升 Y。

每个涉及有效文件的普通提交必须在正文中填写且仅填写一次：

```text
fix(settings): adjust update confirmation

Change-Kind: fix
Change-Reason: 修正既有更新检查的确认流程和状态提示，没有新增独立业务能力。
```

类别取上表的六个值之一，理由必须说明实际行为或兼容性变化。先对照需求和差异确认“是否不兼容、是否新增独立能力、是否仅调整现有能力”，再填写分类；不能按改动行数、文件数量或“新增”关键词猜测。程序不会理解任意业务代码的语义，可靠依据是明确分类、理由和校验，而不是简单的标题关键词匹配。

- 升 X 的提交还必须有 `!` 或非空的 `BREAKING CHANGE:` / `BREAKING-CHANGE:` 声明；带有不兼容声明的提交不能用其他分类或纠正记录降级。
- `feature` 必须涉及 `lib/`、`android/`、`ios/`、`assets/` 或 `pubspec.yaml` 等应用文件；纯测试、CI、脚本维护不能声明为应用新能力。
- 缺少类别或理由、重复声明、未知类别、兼容性声明矛盾时，停止候选分配，不能静默回退到某个版本级别。纯文档、普通合并和已登记的自动版本提交不要求这些正文项；合并冲突引入的额外业务改动应单独提交并分类。
- 混合多个有效提交采用最高级别：`breaking > feature > fix/enhancement/performance/maintenance`；存在真正的新能力时，不能被其他修复提交或单项纠正压低。
- 正式发布前连续提交多个修复，应用版本仍可保持 `1.0.1`，仅递增构建号。
- 忽略普通合并提交和已登记的自动版本提交，避免重复计算。
- 新增的非合并提交必须符合提交规范；不符合时报告具体提交并停止版本准备，不猜测变更级别。
- 若待构建分支尚未包含最近正式版本，先停止并要求同步，避免基于过期版本发布。

### 已推送但未发布的分类纠正

使用 [`.release/change-classifications.json`](../.release/change-classifications.json) 记录纠正：`base_tag` 指定正式版本基线，`commit` 必须为完整 40 位 SHA，`kind` 与 `reason` 记录正确类别及依据。纠正仅作用于该基线后的指定有效提交；目标不存在、重复、属于自动版本提交或仅文档改动时拒绝分配。旧基线记录保留用于审计，不影响后续正式版本的计算。

不重写已推送提交、不删除候选台账、不回收构建号，也不直接手改 `pubspec.yaml`。提交纠正记录后，由候选流程重新计算 X.Y.Z 并分配更大的构建号；即使应用内容指纹相同，也不能复用版本分类不同的候选。候选摘要保存原始类型、有效类型、实际类别、升级幅度、理由及分类来源。

本次纠正：`41b454435857d33bd3008440c846f4aa2557da92` 的更新确认和提醒调整按维护者要求归为 `fix`，从正式版 `1.3.0` 计算得到 `1.3.1`；错误候选 `1.4.0+40` 仅保留审计记录，新候选使用大于 40 的构建号。发布校验会拒绝分类已被纠正的旧候选，不重新发布其安装包。已正式发布的版本与历史分类不追溯改号。

提交后、推送前可用 `python -m scripts.versioning.prepare --branch dev --source <完整提交SHA> --check-only` 检查计划版本和逐提交分类；需要与候选工具相同的 `GITHUB_REPOSITORY`、`GH_TOKEN` 环境。此模式读取台账及 Git 引用，不分配编号、不改写分支、不派发构建。

### 内部构建号 `+N`

使用仓库级统一计数器，不使用 Android、iOS 各自的 Actions 运行序号。

- 初始已发布构建号为 `1`，首个新候选从 `+2` 开始。
- 每个新候选分配一个更大的构建号，Android、iOS 使用同一值。
- 同一候选的失败重试不升号。
- `dev → main` 晋升不升号。
- 已分配的编号不回收；失败或中止可能留下空号，但不会重复或倒退。

示例：

| 操作 | 完整版本 |
|---|---|
| `dev` 新增一个修复候选 | `1.0.1+2` |
| Android 或 iOS 构建失败后重试 | `1.0.1+2` |
| `dev` 再次修改代码，生成新候选 | `1.0.1+3` |
| 将该候选合并到 `main` | `1.0.1+3` |
| 在尚未正式发布前增加新功能 | `1.1.0+4` |

### 怎样判断“同一候选”

为每个候选记录候选 ID、版本、构建号、源提交、最终构建提交和构建内容指纹。

- 指纹依据已跟踪文件计算，排除文档及自动生成的版本记录，并对 `pubspec.yaml` 的版本行单独处理。
- `main` 包含候选提交，且构建内容与该候选一致时，复用原候选。
- 合并冲突解决或额外改动导致内容变化时，生成新候选。
- 默认继续采用快进合并；普通合并也可识别已有候选。Squash/rebase 导致原候选提交不再被保留时，重新准备候选。

**相同版本不代表重新编译的文件逐字节相同。正式发布始终采用用户验证过的那两份产物。**

## 3. 统一版本准备与构建流程

新增统一的版本准备工作流，作为正式候选的唯一编号入口：

```text
推送 dev / main
        ↓
检查是否有有效改动、是否已有候选
        ↓
计算版本 → 分配或复用构建号
        ↓
回写版本并登记候选
        ↓
分发同一候选给 Android、iOS 构建
```

### 版本准备

- 监听 `dev`、`main` 的有效推送，并提供手动入口。
- 将候选分配台账保存在 `version-state`，记录递增计数及候选映射。
- 编号分配串行执行，更新台账时检查旧提交，防止并发覆盖和重复编号。
- 自动版本提交只修改版本配置和候选记录，不修改业务代码。
- 写回前核对目标分支仍对应本次源提交；分支已经前进时停止旧任务，不覆盖新代码。
- 分配和写回过程记录阶段状态，中断后恢复同一候选，不重复占号。
- 不依赖自动提交再次触发 `push`，而是显式启动两平台构建，避免触发循环。

### 两平台构建

保留现有 Android、iOS 工作流文件名，以及 `app-release.apk`、`OViewer.ipa` 产物名称。

- 分支推送后的候选构建改由统一准备的workflow调度，避免原有入口重复构建。
- 手动重试选择已登记的候选，不单独分配版本。
- 两平台检出同一个最终候选提交，从其 `pubspec.yaml` 读取版本。
- PR 只执行验证，不分配正式候选编号、不使用正式签名密钥，其产物不能发布。
- 保留 Flutter 3.16.0 和当前 iOS 12 部署目标。
- 构建前执行测试和静态分析，记录既有提示基线，阻止新增错误和警告。

每次构建上传额外的 `build-metadata` artifact，包含：

- 候选 ID、平台和实际构建提交；
- 应用版本、构建号；
- 工作流运行 ID 和运行次数；
- 安装包名称、大小、SHA-256；
- Android 签名证书指纹。

本地 iOS 安装工具需要适配“源提交 → 候选提交 → iOS 构建”的关联，以及工作流调度事件变化。其文件继续保留在本地，不纳入 Git。

## 4. 应用版本显示与固定签名

### 应用内版本显示

- 引入兼容当前 SDK 的 `package_info_plus 4.2.0`。
- 设置页读取实际安装包版本，显示为 `1.0.1 (3)`，移除写死的版本字符串。
- 异步读取不阻塞启动，中英文界面共用同一份版本数据。
- 读取失败显示“版本信息不可用”，不显示虚假的固定版本。

### Android 正式签名

- 新建长期使用的签名密钥，保持当前应用 ID 不变。
- 密钥保存在仓库外，并由用户保管独立备份。
- 配置四项 Actions Secrets：`ANDROID_KEYSTORE_BASE64`、`ANDROID_KEYSTORE_PASSWORD`、`ANDROID_KEY_ALIAS`、`ANDROID_KEY_PASSWORD`。
- 证书指纹保存为仓库变量 `ANDROID_SIGNING_CERT_SHA256`，供构建和发布核验。
- 正式候选缺少签名配置时直接失败，不回退到 debug 签名。
- 普通本地调试继续使用 debug 签名；CI 中的正式密钥只在临时目录还原，结束后清理。

iOS 继续提供未签名 IPA，本次不接入 Apple 签名和商店发布。

## 5. 正式发布与发布记录

新增独立发布工作流，保留三个必填输入：

| 输入 | 用途 |
|---|---|
| `version` | 确认待发布版本，例如 `v1.0.1`，不参与升号计算 |
| `android_run_id` | 选择已验证的 Android 构建 |
| `ios_run_id` | 选择已验证的 iOS 构建 |

提供额外的“只校验”模式，不创建标签或 Release。

正式发布时：

1. 检查两个运行均来自本仓库指定工作流，成功且不是 PR 构建。
2. 检查两者属于同一候选，实际构建提交一致，并已包含在 `main` 中。
3. 检查输入版本、源码配置、元数据和安装包内部版本一致；版本与构建号满足递增要求。
4. 下载未过期产物，核验文件大小、SHA-256 和 Android 签名。
5. 创建或恢复草稿，原样上传两个安装包及发布清单。
6. 再次校验附件，将标签固定到候选提交，并公开 Release。

发布任务串行执行。失败保留草稿，重试只补齐缺失附件。遇到同名正式 Release、错误标签或附件不一致时停止，不覆盖、不移动标签、不自动删除已有内容。

删除当前“标签触发重新构建及上传 Release”的逻辑，避免覆盖已验证安装包。

### 更新日志与 Issues

- 新增 `CHANGELOG.md`，保留 `Unreleased`，按新增、修复、变更、已知限制分类。
- 根据提交记录生成候选摘要，允许人工补充用户可读说明。
- 发布说明采用候选中已确认的日志，追加构建来源、提交 SHA、校验信息及安装说明。
- 最终 Release 说明省略正文为空的章节及标题（包括空的“变更”“已知限制”和候选摘要）；保留非空章节及原始候选记录，`Unreleased` 模板可继续使用空分类。
- Issues 用版本 Milestone 归类；编号保持固定。
- 已完成 issue 不等于已经发布，正式分发记录以 Release 为准。
- 发布后不替换同版本安装包；修复或回退功能均通过新版本交付。

日常操作简化为：

1. 按规范向 `dev` 提交代码。
2. 每次推送后检查候选准备任务并快进拉取自动版本提交，再获取统一编号的 Android、iOS 候选包并测试。
3. 将验证通过的候选同步到 `main`。
4. 手动选择对应构建，启动正式发布。
5. 发布成功后归档更新日志、关闭对应 Milestone，将收尾提交完整同步到本地及远端 `main`；等待候选准备任务结束、拉取最新进度，确认本地及远端 `main`、`dev` 四个分支的 HEAD SHA 完全一致。

## 6. 验收与落地顺序

必须覆盖以下验证：

- 每次推送后已检查候选准备状态，自动版本提交已拉回本地；正式发布前及收尾后本地、远端 `dev` 与 `main` 四个分支完全一致。
- 提交类型、混合提交和不兼容变更的版本计算。
- 文档变更不升号，自动版本提交不形成循环。
- 两平台并发准备不会重复分配编号。
- 失败重试复用候选；写回中断能够恢复。
- `dev → main` 保持相同完整版本；合并产生额外改动时生成新候选。
- 安装包、源码、元数据和应用内显示版本一致。
- 构建失败、产物过期、版本或提交不一致、签名错误时拒绝发布。
- 草稿恢复、重复发布保护和附件哈希校验。
- 标签发布不再触发额外构建。
- 回归现有 Flutter 测试和本地 iOS 下载、安装流程。
- Android 真机验证同一正式密钥签名的递增版本能够覆盖升级并保留数据。

实施顺序：

**版本规则与台账 → 统一候选准备 → 两平台构建接入 → 动态版本显示与正式签名 → 独立发布 → 集成及真机验证。**

先在 `dev` 验证，再同步 `main` 启用。实施过程中不修改既有 `v1.0.0`，也不自动发布新版本。
