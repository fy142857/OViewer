# 账号登录验证记录（Issue #61）

## 当前交互

- 登录页默认进入“账号登录”，右侧依次保留 WebView 登录、手动 Cookie。
- 用户补充要求区分自动加载检查与人工 CAPTCHA，随后明确接受在账号页内临时显示验证区域，不切换 WebView 标签、不重复输入账号密码。
- 用户名去除首尾空白，密码保持原样；密码只存在于本次操作及应用输入框，切换登录标签、离开页面或成功后清空。
- 账号输入框使用普通文本类型并允许输入建议，关闭自动纠错，交由用户默认输入法处理；密码框继续使用安全输入。厂商安全键盘的实际切换仍由系统决定。
- 账号页内复用现有 LoginWebView。站点自行执行自动检查；出现人工验证时由用户在区域内处理，应用不自动点击 CAPTCHA。
- 正常等待上限 40 秒；用户开始操作验证区域后，本次等待上限延长至 2 分钟。超时或平台不支持时使用中性提示，允许重试或手动进入原 WebView 登录。
- 注册入口通过独立原生接口在系统浏览器打开官方注册页面。

## 登录与会话

- 先在真实浏览器里获取可提交的登录表单及其验证字段，不再预先向论坛登录页发送普通 HTTP GET。
- 验证页只按站点原流程加载；原生页面标题表明已进入普通登录页后，才读取表单。网页用户名和密码字段为只读，浏览器不提交登录表单。
- 保留该次表单的 action、隐藏字段、会话参数和一次性验证值。不会重新 GET 一张缺少已完成验证值的表单。
- 只从浏览器带回 cf_clearance / __cf_bm 和实际浏览器 UA；不导入浏览器认证 Cookie。准备结果不落盘。
- 使用独立的内存 Cookie 容器，通过严格 HTTPS 校验向官方论坛提交一次账号密码；拒绝外站、降级、307/308 重放密码及无限重定向。POST 后遇到验证不会自动重发密码。
- 完整认证 Cookie 加上独立论坛页面中的对应会员链接和退出入口共同确认成功，之后沿用应用的会话保存机制。
- Android 的验证区域临时使用应用选定代理，检查结束恢复 WebView 原状态；网络配置变化、取消、离开页面和退出登录都使旧结果失效。过期关闭请求不会释放新的验证会话。
- 会话写入在多个阶段检查操作是否仍有效，取消后清理本次部分认证数据；完成回调与最后一次有效性检查之间不再等待异步操作。
- EH 模式不请求 EX。EX 检查失败时保留已成功的账号登录和当前站点，不自动切站。

## 官方表单依据

2026-10-23 读取官方论坛 act=Login&CODE=00 页面的 DOM，未提交账号密码：

- POST 到官方论坛 /index.php，操作 act=Login&CODE=01，带页面当次返回的 s。
- 用户名与密码字段为 UserName、PassWord；隐藏字段为 referer、b、bt。
- CookieDate=1 默认选中，Privacy=1 默认不选中，提交按钮为 submit=Log me in。
- 注册入口为 /index.php?act=Reg&CODE=00，不固化用户提供的会话参数。
- 登录表单中实际包含 cf-turnstile 组件。组件存在以及普通页面的 JSD 脚本都不等于必须人工验证；完成状态取真实浏览器生成的表单验证字段。
- test/fixtures/account_login_form.html 保留核实过的字段结构，替换会话和 referer；协议测试的认证响应、验证值均为合成样本。
